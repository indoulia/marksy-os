# Direct-to-Upstox Market Data (On-Device) — Design

## Context

Following sub-project 1 (Marksy Intelligence Android UI), the product direction has
been clarified: Marksy and Upstox are two independent, unrelated data sources from
the app's perspective. Marksy is the **advisor** — recommendations/predictions and
IPO intelligence, server-computed, read via the existing scoped `marketApiKey`.
Upstox is the **actor** — market data now, and (in a future, separate piece of work)
trade execution under each user's own brokerage identity, which is why this
credential must live on the user's device rather than be proxied through a shared
server-side connection: a single centralized token cannot represent many users'
individual trades.

This design covers only the market-data piece: reading live quotes and historical
candles directly from Upstox using a user-supplied Analytics Token. It does not
cover order placement (Tradsy remains out of scope, per every prior decision in
this project) or the Upstox WebSocket live feed (deferred — see Non-goals).

## Goals

- A new user-owned credential — the Upstox **Analytics Token** (read-only, ~1-year
  validity, generated by the user in Upstox's own developer console, per
  `marksy-api`'s own `app/upstox_credentials.py` EPIC-309 documentation) — stored
  on-device only, entered via QR scan or manual paste.
- Direct REST calls from MarksyOS to Upstox for LTP quotes and historical candles,
  using that token.
- This **runs alongside** the existing marksy-api-sourced market data (Overview,
  Stock detail) rather than replacing it: when a user has configured their own
  Upstox token, screens prefer Upstox-sourced price data; otherwise they fall back
  to the existing marksy-api path unchanged. No field-level merging between the two
  sources — a whole-source preference, honestly labeled ("Data: Upstox" vs
  "Data: Marksy").
- Symbol → Upstox instrument key resolution via marksy-api's own instrument catalog
  (`Stock.instrument_key`, already persisted server-side) rather than an unverified
  Upstox instrument-search endpoint — Marksy acts as the catalog, Upstox does the
  market-data work.

## Non-goals (deferred)

- The Upstox V3 WebSocket live feed. Verified via research: it is **protobuf-encoded**
  (not JSON), requires a two-step REST-authorize-then-connect handshake, and needs a
  protobuf parsing dependency this codebase does not currently have — a genuinely
  different class of work from the REST calls here. Its own future sub-project.
- Any trading/order-placement capability. The Analytics Token is documented as
  read-only; a future trading credential (Upstox's OAuth-based access token, which
  does support order placement but expires daily) is a separate, later piece of work
  when Tradsy becomes real.
- Any marksy-api change beyond exposing the existing `Stock.instrument_key` value on
  a response the app can call — no new marksy-api capability, no new Upstox logic
  server-side.
- Replacing or modifying the existing `com.marksy.os.market` package, its screens,
  or its tests in any way — this is fully additive, in a new, independent package.

## Architecture

### marksy-api change (small, additive)

`api/schemas/instruments.py`'s `InstrumentLifecycle` gains one new optional field,
`instrumentKey: str | None`, sourced from `Stock.instrument_key`. Existing clients
ignore unknown fields; this is non-breaking. (Exact wiring — service function,
migration if any — to be confirmed when this piece is planned; likely no migration
needed since the column already exists per `app/models.py:12`.)

### MarksyOS: new `com.marksy.os.upstox` package

- `UpstoxCredentialStore` — mirrors `SecureCredentialStore`'s existing
  Keystore-encrypted pattern exactly (own preference keys, own alias reuse), holding
  the Analytics Token. A new Gateway Settings block, matching the just-built and
  just-reordered Marksy-key block's pattern (masked field, Show/Hide, Save/Remove),
  plus QR-scan support extending the existing `GatewayQrParser`.
- `UpstoxApiClient` — `HttpURLConnection`-based, matching every existing client in
  this codebase (`MarksyTipsApiClient`, `RealMarketApiClient`). Base URL
  `https://api.upstox.com/v3`. Two methods:
  - `ltpQuote(instrumentKeys: List<String>): Map<String, LtpQuoteDto>` →
    `GET /market-quote/ltp?instrument_key=<comma-separated>`
  - `historicalCandles(instrumentKey: String, unit: String, interval: Int, from: String, to: String): List<CandleDto>` →
    `GET /historical-candle/{instrument_key}/{unit}/{interval}/{to_date}/{from_date}`
  - Auth: `Authorization: Bearer <token>` header, HTTPS enforced at construction
    (same pattern as `RealMarketApiClient`).
- Instrument-key resolution: `MarketApiClient` (the existing one, Task 5) gains one
  new method reading `instrumentKey` off the existing `/instruments/{symbol}`
  response (once marksy-api exposes it) — no new marksy-api endpoint, no new
  MarksyOS-side marksy client method beyond a field addition to the existing
  `InstrumentLifecycleDto`.
- `UpstoxMarketRepository` — wraps `UpstoxApiClient`, returns the existing
  `MarketDataState<T>` sealed type (reused as-is from `com.marksy.os.market`, not
  duplicated) so screens handle it identically to the marksy-sourced state.

### Run-alongside behavior in existing screens

`MarketOverviewScreen`/`StockDetailScreen` (Tasks 7-8, unmodified in structure) gain
one additional data attempt: if `UpstoxCredentialStore` has a token configured, the
screen's data-loading step tries `UpstoxMarketRepository` first for price fields; on
`Unavailable`/`Error` from that path, or when no token is configured at all, it falls
back to the existing `MarketIntelligenceRepository` (marksy-api) path exactly as
today. The freshness footer text distinguishes the two ("Data: Upstox" vs
"Data: Marksy") so a user always knows which source they're looking at.

## Testing

Same conventions as sub-project 1: pure DTO/parse functions unit-tested with
realistic fixture JSON (LTP response, candle array); `UpstoxCredentialStore` tested
like `SecureCredentialStore` (round-trip, independence from the other two
credentials); Compose screen tests for the source-preference branching
(Upstox-configured-and-available, Upstox-configured-but-unavailable-falls-back,
Upstox-not-configured-uses-marksy-directly).

## Risks / open items carried into planning

- Exact `InstrumentLifecycle`/`Stock.instrument_key` wiring details (service
  function name, whether a migration is truly unnecessary) to be confirmed by
  reading `api/services/instruments.py` during implementation — not guessed here.
- LTP/OHLC/full-quote response field names beyond `last_price` were not fully
  verified during research; exact DTO field list to be finalized against a real
  response or Upstox's reference page during implementation.
- The "prefer Upstox, fall back to Marksy" decision point (per-screen, per-load, or
  cached for the session) needs a concrete rule chosen during planning — this design
  intentionally leaves it as "try Upstox first" without over-specifying retry/cache
  behavior, to avoid guessing at requirements not yet discussed.
